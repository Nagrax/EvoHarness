# 把 EvoHarness 当试验场：架构设计对照（第一份真实证据）

> 2026-10-26。用户诉求：EvoHarness 应成为**试验场**，在真实任务上比较不同 harness 设计
> （Claude Code 式重封装 / pi-agent 式轻量 / DSH 式插件化），并回答"收益能否覆盖 token 成本"。

本文记录**已执行**的对照与结论边界，不包含未做的部分。

---

## 一、先解决"能不能比"的问题

比较三种设计的前提是：它们的差异必须是**真实可配置的行为**。
第一次做的时候我踩了这个坑：

`eval/arch_compare.py` 初版把 `EVOHARNESS_DISABLE_TOOL_HINTS` 当成设计差异，
但查代码发现 `get_active_tool_definitions(self.tools)` 默认 `with_hints=False`——
**工具安全注解根本没有进入模型请求**。把它算作"重封装 vs 轻量"的差异是错的。

同时 `EVOHARNESS_DISABLE_MEMORY_PREFETCH` 也**不存在**，只是个名字。

修复：
1. 新增真实开关 `EVOHARNESS_DISABLE_MEMORY_PREFETCH`，接进 **Anthropic 与 OpenAI 两条路径**
   （只接一处等于半边生效，有回归固定 `count >= 2`）。
2. 把设计维度改成三个**确实影响每轮请求**的开关组合。
3. 新增 `probe_env_support()`：声明前先验证代码里有读取点，`blocked!=null` 即拒绝开跑。
   （这个探针也修过一次：初版只扫 4 个文件，漏了 `tools.py`，把 `MAX_RESULT_CHARS` 误判为纸面参数。）

**现在的状态**：`eval/arch_compare.py plan` 输出 `blocked: null`，三个设计的 env 全部有读取点，
10 条回归固定这一点（`tests/test_arch_compare.py`）。

## 二、三种设计的真实映射

| 设计 | env 组合 | 含义 |
| --- | --- | --- |
| heavy-wrapped | 预取开、折叠线 0.70 | 每轮多一次旁路召回，上下文更全、更贵 |
| lightweight | 预取关、折叠线 0.55 | 省旁路调用、更早折叠 |
| plugin | 预取开、截断 20k | 保留收益侧（召回），只压成本侧（工具输出） |

## 三、已执行对照：heavy-wrapped vs lightweight

题池：`always-pass`（当前配置做得出的题，避免用无区分度题池烧 token）
规模：2 轮 × 1 题（n=2）

| 设计 | pass@1 | tokens | Δpass | Δtok | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| heavy-wrapped | **50.0** | 0.46M | — | — | baseline |
| lightweight | **0.0** | 0.43M | **−50.0** | **−0.03M（省 6.5%）** | negative:quality-loss-outweighs-savings |

### ⚠️ 四、这条结论被后续方差检验推翻了（必须置顶）

在写完上面这张表之后，我对**同一个基线配置**（heavy-wrapped）用同题池、同规模重复跑了一次：

| heavy-wrapped 重复运行 | pass@1 |
| --- | ---: |
| 第 1 次 | 0.0 |
| 第 2 次 | 50.0 |

**同配置极差 = 50pp**（`eval/runs/arch/variance.json`）。

这意味着：上面所有"Δpass = −50"的结论**完全落在噪声范围内**。
在 n=2 的规模下，这套实验**无法区分任何配置差异**。

正确的说法是：
- ❌ 不能说"轻量设计省 token 掉质量"
- ❌ 不能说"关预取有害"
- ✅ 只能说："在 n=2 时，同配置重复运行的极差（50pp）已经覆盖了我们观察到的全部差异，
  因此这些对照**没有信息量**，必须扩样本。"

这是本轮最重要的方法学收获：**方差估计必须与对照实验同时做**，
否则会把噪声当信号，并把它写进结论。

### 五、这条教训对"试验场"意味着什么

用户要的是"看哪种设计更好"。但试验场的第一能力不是"跑出差异"，
而是**知道自己的差异是否可信**。本项目现在具备：

1. `eval/variance_check.py`：同配置重复运行的极差估计；
2. `eval/holdout_calibrate.py`：题池区分度分层；
3. `eval/roi.py`：n<30 一律 not-claimable。

三者合起来构成"防自欺三件套"。缺任何一个，都会把噪声写成发现。

## 四、成本侧的独立发现（与设计无关，但更硬）

`eval/roi.py` 从既有 GAIA/HLE 产物算出：

| 指标 | 值 |
| --- | --- |
| GAIA `tokensPerCorrect` | **1.11M** |
| HLE `tokensPerCorrect` | **1.76M** |
| 进化自身开销占比 | **6.9%** |

含义：**贵的不是进化，是"每题都跑完整 agent 循环"**。
所以任何"优化 harness"的努力，若不能降低**主线每题的 token**，ROI 都不会好看。
轻量设计正是想压这一块——实测省了 6.5%，但代价是质量。

这给出一个可检验的假设（下一步）：
**是否存在"省 30%+ token 且不掉质量"的配置点？** 需要单变量拆解（只关预取、只改折叠线）
而不是打包开关。

---

## 五、下一步（按信息量排序）

| # | 动作 | 成本 | 信息量 |
| --- | --- | --- | --- |
| 1 | 单变量拆解：只关预取 / 只改折叠线，各自测一次 | ~1M | 高：定位到具体机制 |
| 2 | 把 n 提到 30+（用 always-pass 池） | ~10M | 中：可得 CI |
| 3 | plugin 设计 vs heavy-wrapped | ~1M | 高：验证"只砍贵的不砍有用的" |

以上都在 300M 台账内可执行（已用 7.89M，剩 292.1M）。

## 六、诚实边界

- 未读 Claude Code / pi-agent / DSH 的源码或文档，本对比是**按"可配置行为"抽象**的映射，
  不代表三家真实实现的全部差异。
- agent 是否"更聪明"不在本对比范围；只测了同模型下的配置差异。
- n 全部小于 30，所以**没有任何一条可以宣称设计优劣**，只有"这个组合在当前题池上是负收益"这类
  范围明确的陈述。
